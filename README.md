# CreatorInsight AI：抖音创作者复盘增长助手

CreatorInsight AI 是一个面向短视频创作者增长场景的 AI 复盘工作台。它尝试解决一个具体问题：创作者发布内容后，能看到播放量、完播率、点赞率、评论率、收藏率等数据，但很难把这些数据转化为下一条内容的具体优化动作。

项目关注的不是单次内容生成，而是「发布后复盘 → 问题归因 → 下一条内容建议 → 持续迭代」这一段增长链路。

## 1. 项目背景

在短视频创作中，很多创作者会遇到类似问题：

- 播放量有时高、有时低，但不知道差异来自哪里。
- 完播率低，不确定是开头弱、节奏慢，还是视频时长不合适。
- 收藏率不错，但评论率低，不知道如何增强互动。
- 看了很多平台数据，却不知道下一条内容应该先改什么。

CreatorInsight AI 的目标，是把这些离散数据翻译成更可执行的内容运营建议。

## 2. 产品定位

CreatorInsight AI 是一个轻量级 AI 创作者复盘工具。

用户输入：

- 账号定位 / 内容垂类
- 目标人群
- 创作者阶段
- 当前增长目标
- 近几条作品的核心数据

系统输出：

- 账号健康分
- 当前核心问题归因
- 表现最佳 / 最弱作品判断
- 下一条内容选题、标题、开头、结构、互动建议
- 7 天增长计划

## 3. 核心业务思路

项目把创作者增长拆成一个简化闭环：

```text
作品发布
  ↓
数据回收
  ↓
问题归因
  ↓
下一条内容建议
  ↓
小步实验
  ↓
再次复盘
```

其中最容易断掉的是「数据回收 → 问题归因 → 下一条动作」。

例如：

- 播放高、完播低：选题或标题有吸引力，但内容承接不足。
- 完播高、点赞低：用户愿意看完，但观点、情绪或共鸣不足。
- 收藏高、评论低：干货价值强，但互动设计不足。
- 播放低、互动高：内容质量可能不错，但标题、封面或选题包装弱。

因此，项目没有让大模型直接自由发挥，而是先用运营指标做基础判断，再让 AI 把判断转化为更自然、更具体的创作者建议。

## 4. 产品机制

### 4.1 指标体系

| 指标 | 业务含义 | 产品判断作用 |
| --- | --- | --- |
| 播放量 | 选题、标题、封面吸引力 | 判断内容是否具备进入流量池的能力 |
| 完播率 | 开头承接、内容节奏、视频时长 | 判断内容是否留得住用户 |
| 点赞率 | 情绪共鸣、观点认同 | 判断内容是否让用户认可 |
| 评论率 | 话题性、互动设计 | 判断内容是否能激发讨论 |
| 收藏率 | 实用价值、长期价值 | 判断内容是否有干货沉淀 |
| 转发率 | 社交传播价值 | 判断内容是否值得分享 |

### 4.2 账号健康分

健康分满分 100，当前版本用简化规则模拟：

```text
播放表现 20 分
完播表现 25 分
互动表现 25 分
收藏表现 20 分
稳定性 10 分
```

健康分不是平台真实评分，而是用于展示「数据驱动诊断」的产品思路。

### 4.3 AI 生成机制

项目采用：

```text
前端数据录入
  ↓
规则诊断兜底
  ↓
后端代理调用 OpenAI 兼容接口
  ↓
大模型生成复盘建议
  ↓
前端结构化展示
```

这样设计有两个考虑：

1. **可控性**：规则诊断保证输出不会完全失控。
2. **可用性**：即使模型接口失败，页面仍能展示基础诊断结果。

## 5. 功能模块

### 创作者画像

输入账号定位、目标人群、创作者阶段和当前目标，让 AI 建议更贴近真实场景。

### 作品数据编辑

支持编辑多条视频数据：

- 视频标题
- 内容类型
- 播放量
- 完播率
- 点赞率
- 评论率
- 收藏率
- 转发率

### AI 复盘诊断

系统会输出：

- 当前账号核心问题
- 内容表现归因
- 表现最佳作品
- 需要优先优化的作品
- 各指标表现条形图

### 下一条内容建议

AI 会生成更具体的创作建议：

- 推荐选题
- 标题方向
- 前 3 秒开头
- 内容结构
- 互动引导
- 补充建议

### 7 天增长计划

将复盘结论转化为一周行动计划，帮助创作者进入持续迭代节奏。

## 6. 技术实现

项目刻意保持轻量，重点放在产品思路和业务闭环上。

| 模块 | 实现 |
| --- | --- |
| 前端 | 原生 HTML / CSS / JavaScript |
| 后端 | Node.js 原生 HTTP 服务 |
| AI 接口 | OpenAI 兼容 Chat Completions |
| 数据存储 | 当前版本不做数据库，使用前端状态和示例数据 |
| 安全处理 | API Key 只放在后端环境变量中，前端不暴露 |

## 7. 如何运行

### 1. 准备环境变量

复制示例文件：

```bash
cp .env.example .env
```

填写模型服务配置：

```bash
OPENAI_BASE_URL=https://your-openai-compatible-endpoint
OPENAI_MODEL=your-model-name
OPENAI_API_KEY=your-api-key
PORT=4184
```

### 2. 启动服务

```bash
npm install
npm start
```

如果不需要安装依赖，也可以直接运行：

```bash
node server.js
```

### 3. 打开页面

```text
http://localhost:4184
```

## 8. 如何部署到公网

这个项目不能只用 GitHub Pages 部署。原因是页面需要调用大模型接口，而 API Key 不能放在浏览器前端里。

推荐部署方式是：

```text
GitHub 仓库
  ↓
Node.js Web Service
  ↓
配置环境变量
  ↓
生成公网 URL
```

部署时需要设置这些环境变量：

| 变量 | 说明 |
| --- | --- |
| `OPENAI_BASE_URL` | OpenAI 兼容接口地址，不需要在末尾手动加 `/v1` |
| `OPENAI_MODEL` | 使用的模型名称 |
| `OPENAI_API_KEY` | 模型服务密钥，只放在服务器环境变量中 |
| `PORT` | 服务端口，部署平台通常会自动注入 |

部署平台的启动命令：

```bash
npm start
```

健康检查路径：

```text
/health
```

上线后，用户访问公网 URL，就可以直接填写内容并生成整段复盘分析。

## 9. 当前版本边界

当前版本主要用于验证产品机制和交互闭环，因此做了刻意收敛：

- 不接入真实平台数据 API。
- 不做登录和多账号管理。
- 不做数据库存储。
- 不模拟真实推荐系统。
- 不将健康分解释为真实平台评分。

## 10. 公网使用时需要注意

如果开放给所有人使用，需要额外关注：

- **费用控制**：公开访问会消耗模型调用额度，建议增加调用频率限制。
- **滥用防护**：建议加验证码、访问密码或简单登录。
- **内容安全**：用户输入可能包含无关或不合规内容，需要增加输入过滤。
- **隐私提示**：不要让用户输入真实个人隐私、账号密码或未公开商业数据。
- **稳定性**：建议记录错误日志，但不要记录 API Key。

## 11. 后续可迭代方向

- 增加内容安全和合规检查模块。
- 支持导出复盘报告，方便复盘和协作。
- 加入 AI 输出评分机制，评估建议的准确性、可执行性和满意度。
- 支持多垂类案例库，将优秀内容结构沉淀成可复用模板。
